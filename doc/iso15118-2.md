# ISO 15118-2 (2013) for Clara

Scope: ISO 15118-2:2013 ("iso1"), DC, external payment (EIM), over plain TCP. No TLS, no Plug & Charge, no
certificates, no value-added services.

## Using it

The default build contains DIN 70121 and ISO 15118-2. What the car offers is a parameter:

| `V2gProtocols` (ID 38) | SupportedAppProtocolReq |
|---|---|
| 0 = DinOnly (default) | DIN 70121 only: the same stored request (recorded from an Ioniq) as before |
| 1 = IsoThenDin | ISO 15118-2 priority 1, DIN 70121 priority 2 |
| 2 = DinThenIso | DIN 70121 priority 1, ISO 15118-2 priority 2 |
| 3 = IsoOnly | ISO 15118-2 only |

Schema IDs: 1 for DIN 70121 (`urn:din:70121:2012:MsgDef`), 2 for ISO 15118-2 (`urn:iso:15118:2:2013:MsgDef`), both
version 2.0. The value `V2gProtocol` (ID 2041) shows the charger's choice: 0 = None, 1 = DIN70121, 2 = ISO15118_2.
One protocol per session, fixed by the SupportedAppProtocolRes. The parameter is read when the TCP connection
starts.

New stop reasons:
* 10 = ChargerRequiresTls: the SDP response says TLS (security 0x00) and `V2gProtocols` is 3 (ISO only). While DIN
  70121 is offered (0, 1, 2), a TLS answer is only traced and Clara tries plain TCP, as before: DIN has no TLS, and a
  DIN charger that answers 0x00 by mistake may still accept plain TCP.
* 11 = NoCommonProtocol: the charger chose none of the protocols offered, or a schema that wasn't offered.
* 12 = V2gMessageError: an ISO message couldn't be encoded or decoded, or lacks what the session needs; or, for both
  protocols, the receive path stopped on an invalid V2GTP header or a message larger than its buffer.
* 13 = ChargerResponseFailed: an ISO response with ResponseCode FAILED or FAILED_...

`make ISO1=0` builds DIN 70121 only, without the iso1 codec. `V2gProtocols` then has no effect.

## The ISO session

| Step | Request | What Clara does with the response |
|---|---|---|
| 1 | SessionSetupReq: session ID 0 (8 bytes), EVCCID = our MAC address | keeps the session ID |
| 2 | ServiceDiscoveryReq: ServiceCategory EVCharging | needs ExternalPayment and DC_extended; keeps the charge service's ServiceID |
| 3 | PaymentServiceSelectionReq: ExternalPayment, the charge service only | |
| 4 | AuthorizationReq: no Id, no GenChallenge | repeats (built again) while EVSEProcessing is Ongoing, up to 120 times |
| 5 | ChargeParameterDiscoveryReq: DC_extended, MaxEntriesSAScheduleTuple 5 | needs a SAScheduleList; keeps the first tuple's SAScheduleTupleID |
| 6 | CableCheckReq, PreChargeReq | as DIN |
| 7 | PowerDeliveryReq: ChargeProgress Start, that SAScheduleTupleID, no ChargingProfile | |
| 8 | CurrentDemandReq | as DIN; ReceiptRequired is ignored |
| 9 | PowerDeliveryReq: ChargeProgress Stop, the same SAScheduleTupleID | |
| 10 | WeldingDetectionReq | as DIN |
| 11 | SessionStopReq: ChargingSession Terminate | |

Every ISO response's ResponseCode is checked. OK, OK_NewSessionEstablished, OK_OldSessionJoined and
OK_CertificateExpiresSoon go on. FAILED and every FAILED_... end the session with ChargerResponseFailed: in
CurrentDemand with one PowerDeliveryReq Stop and the normal end (as for a malfunction); in any other state with the
safe shutdown.

Never sent: ServiceDetailReq, CertificateInstallationReq, CertificateUpdateReq, MeteringReceiptReq, ChargingStatusReq.
The values sent (limits, SOC, target voltage and current, EVReady) are the ones DIN sends.

## How it's built

One state machine (`ccs/pevStateMachine.cpp`) runs both protocols. Right after decoding, the response is read into
a protocol-neutral `struct pevResponse` (`ccs/pevMessages.h`): which response it is, ResponseCode OK, EVSEProcessing
Finished, the DC_EVSEStatusCode, a stop request from the charger, and the voltages and currents. The states decide on
that only. The requests are built per protocol: DIN in `pevStateMachine.cpp` as before, ISO in `ccs/pevIso1.cpp`.
`exi/appHandRequest.c` builds the SupportedAppProtocolReq and reads the answer; `test/host/apphand_test.cpp` checks
both on a PC (`make -C test/host`), including that the DIN-only request it builds is the stored Ioniq request.

So every safety step is the same code for both protocols:

| Safety step | DIN 70121 | ISO 15118-2 |
|---|---|---|
| Stop on enable off, button or accu full (CurrentDemand) | `hardwareInterface_stopChargeRequested()`, `getIsAccuFull()` | same code |
| Charger asks to stop | EVSEStatusCode EVSE_Shutdown | same code; also EVSENotification StopCharging |
| EVSE_Malfunction (6), EVSE_EmergencyShutdown (5) | PowerDeliveryReq off, then wait for its response | same code (DIN and ISO number the status codes alike) |
| Inlet voltage deviation | `hwIf_isInletVoltageError`, PowerDeliveryReq off | same code |
| One request at a time after a stop | no CurrentDemandReq after PowerDeliveryReq off | same code |
| Connector lock before CableCheck | `WaitForConnectorLock` | same state |
| End of precharge, contactors | inlet vs accu voltage, EVSEMinimumVoltage, 450 ms before PowerDeliveryReq | same state |
| Normal end | PowerDeliveryRes, state B, 300 ms, contactors open | same state |
| Welding detection | below 40 V, at most 10 rounds | same state |
| Unlock | after welding detection, or at the end of the safe shutdown | same states |
| Timeouts per state | `STATE_LIST` | same table |
| Safe shutdown | state B, 2 s, contactors open, 1 s, unlock | same states |
| TCP lost | state B, contactors open | same code |
| Charger answers ResponseCode FAILED... | not read (as main) | in CurrentDemand: PowerDeliveryReq off as for a malfunction; elsewhere: safe shutdown. StopReason ChargerResponseFailed |
| Invalid V2GTP header, message larger than the buffer | receiving stops, nothing more acknowledged; safe shutdown, StopReason V2gMessageError | same code |

What differs: an ISO message that can't be encoded or decoded, or that lacks what the session needs (no ExternalPayment
or DC_extended in ServiceDiscoveryRes, no SAScheduleList), stops at once: a trace message, StopReason
V2gMessageError, then the safe shutdown. A DIN response that doesn't decode is ignored as before, and the state's
timeout leads to the same safe shutdown. ISO response codes are checked (above); DIN response codes are not read, as
on main.

## Open points

Not changed here; possible separate changes:
* **DIN response codes.** Main doesn't read them except in CableCheckRes, so a DIN charger's FAILED answer goes on
  like OK (until a status code or a timeout stops the session). Checking them as for ISO would be a change to DIN
  behaviour, so it belongs in its own change.
* **Charger faults outside CurrentDemand.** A DC_EVSEStatusCode of EVSE_Malfunction or EVSE_EmergencyShutdown in
  CableCheckRes, PreChargeRes or PowerDeliveryRes is only acted on once CurrentDemand runs. Same for DIN on main.
* **Timeouts.** The ISO session uses DIN's timeouts per state (`STATE_LIST`). Some may be longer than ISO
  15118-2's; not checked against the standard, so not changed.
* **EVSENotification ReNegotiation** is ignored: there is no renegotiation.

## The iso1 codec

It is the OpenV2G codec from the `iso-test` branch, trimmed the same way as the DIN codec:
* no header signature;
* only `V2G_Message` at document level;
* the encoder only for the requests an EV sends, the decoder only for the responses it gets;
* the body union only for the messages of a DC EIM session: SessionSetup, ServiceDiscovery, PaymentServiceSelection,
  Authorization, ChargeParameterDiscovery, CableCheck, PreCharge, PowerDelivery, CurrentDemand, WeldingDetection
  and SessionStop.

DIN and ISO share one memory area (a union). The codec's own limits are kept as generated. A response with more than
this fails to decode, and the session stops with V2gMessageError:
* ServiceList: 8 services. Value-added services offered by the charger are decoded and ignored.
* PaymentOptionList: 2 options.
* SAScheduleList: 3 tuples, each with up to 5 PMaxSchedule entries and an optional SalesTariff of up to 5 entries.
  ChargeParameterDiscoveryReq asks for at most 5 (MaxEntriesSAScheduleTuple).
* Signed messages (a header signature, for example a signed SalesTariff) don't decode.

## One document for encoder and decoder

`make SHARED_EXI_DOC=1` uses one EXI document for the encoder and the decoder, which saves 13,472 bytes of RAM. With
one document, the decoded response and the next request are in the same memory. Phase 0 found two places on the DIN
path that read a response after the next request had been prepared:
* WaitForContractAuthenticationResponse sent the request again without building it again;
* WaitForCurrentDemandResponse read the status code, voltage and current after a PowerDeliveryReq could have been
  prepared.

Phase 2 removes both: the response is copied into `struct pevResponse` before any request is built, and the
authorization request is built again for every repetition. So the shared document should now work for DIN and ISO,
but it hasn't been tried on a charger; it stays an option. `aphsDoc` (SupportedAppProtocol) is a separate document.
TCP retransmissions use the TCP transmit buffer, not the document.

## What blocked ISO on main (phase 1)

* **TCP receive.** `tcp_rxdata` was 200 bytes, with no reassembly. Now 8 + 1,024 bytes; segments are put together
  into one V2GTP message by sequence number (`ccs/v2gtp.cpp`, tested in `test/host`). The SYN announces an MSS of
  1,000 and the window is the buffer size. Only what is taken is acknowledged:
  * bytes after the end of a message in the same segment (the start of the next one) are not acknowledged, so the
    charger sends them again;
  * a segment that arrives while the last message hasn't been processed is not taken, rather than overwrite it;
  * an invalid V2GTP header (version) or a length larger than the buffer stops receiving: nothing more is
    acknowledged, and the state machine stops the session (above). Skipping by the length could skip, and
    acknowledge, up to 4 GB on a corrupt header.
* **Ethernet receive.** `MY_ETH_RECEIVE_BUFFER_LEN` was 250, and a longer frame was read past the copied data. Now
  1,086 (the SPI buffer less its framing). One SPI read is limited to the SPI buffer (1,098 bytes of data), so with
  several frames waiting in the QCA7000, the last one may be cut: for example a pure ACK and a 1,000-byte segment
  that arrive in the same 30 ms. Main (and the first version of phase 1) took such a frame as whole, with stale bytes
  for its end. Now `ccs/qcaframe.cpp` keeps the part of a cut frame until the next read brings the rest, passes on
  only complete frames with their end-of-frame bytes, drops frames larger than the buffer, and finds the next frame
  start after data that doesn't fit the framing (tested in `test/host`).
* **TCP options.** The payload was copied from a fixed offset. Now from the TCP header length.
* **SDP.** The response's security and transport bytes were not read. They are now; see ChargerRequiresTls above for
  when a TLS answer stops the session. A non-TCP answer is traced, and Clara tries TCP as before.

## Testing on a vSECC

1. On the vSECC (or another test charger), enable ISO 15118-2 DC with external payment (EIM), without TLS.
2. Set `V2gProtocols` = 1 (ISO then DIN) or 3 (ISO only). With 3, a charger without ISO stops with NoCommonProtocol.
3. Charge and stop as with DIN.
4. If the vSECC can answer with a FAILED response code (e.g. FAILED for AuthorizationRes, FAILED_PowerDeliveryNotApplied
   for PowerDeliveryRes, FAILED for CurrentDemandRes), try each: StopReason 13, the safe shutdown or, from
   CurrentDemand, one PowerDeliveryReq Stop.
5. With `V2gProtocols` = 3 and TLS required on the vSECC: StopReason 10 and no TCP connection. With 1: a trace
   message and a plain TCP connection.

In the PLC log or trace, look for:
* SupportedAppProtocolReq with `urn:iso:15118:2:2013:MsgDef` (SchemaID 2) and, for 1, `urn:din:70121:2012:MsgDef`
  (SchemaID 1); the response with SchemaID 2; `V2gProtocol` = 2; "ISO 15118-2 session." in the trace;
* ServiceDiscoveryReq with ServiceCategory EVCharging, PaymentServiceSelectionReq with ExternalPayment and the
  charge service's ServiceID;
* ChargeParameterDiscoveryReq with DC_extended; the SAScheduleTupleID of the response's first tuple coming back in
  both PowerDeliveryReq (ChargeProgress Start, then Stop);
* CurrentDemand loop, WeldingDetection until below 40 V, SessionStopReq with Terminate;
* no CertificateInstallation, MeteringReceipt or ServiceDetail requests;
* for the stops: the charger's stop button (EVSE_Shutdown or EVSENotification StopCharging), the vSECC's Malfunction
  and EmergencyShutdown status, and the car's enable off, each followed by one PowerDeliveryReq Stop and no further
  CurrentDemandReq.

With `V2gProtocols` = 0, the SupportedAppProtocolReq must be byte for byte the one main sends.
