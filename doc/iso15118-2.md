# ISO 15118-2 (2013) for Clara: phase 0, what it costs

Scope: ISO 15118-2:2013 ("iso1"), DC, external payment (EIM), over plain TCP. No TLS, no Plug & Charge, no
certificates, no value-added services.

Phase 0 only measures. The default build is DIN 70121 only, unchanged. The ISO code is built only on request:

* `make ISO1=1` adds the iso1 codec. DIN and ISO share one memory area (a union), as on the `iso-test` branch.
  Nothing selects ISO yet: `projectExiConnector_keepIso1Linked()` only references the codec, behind a flag that is
  never set, so that the linker keeps it and its size can be measured.
* `make SHARED_EXI_DOC=1` uses one EXI document for the encoder and the decoder instead of two. The DIN state machine
  isn't ready for that yet (see "One document for encoder and decoder" below).
* `tools/iso_phase0_report.sh` builds all four combinations and prints the figures below.

## The iso1 codec

It is the OpenV2G codec from the `iso-test` branch, trimmed the same way as the DIN codec on main:
* no header signature;
* only `V2G_Message` at document level;
* the encoder only for the requests an EV sends, the decoder only for the responses it gets;
* the body union only for the messages of a DC EIM session: SessionSetup, ServiceDiscovery, PaymentServiceSelection,
  Authorization, ChargeParameterDiscovery, CableCheck, PreCharge, PowerDelivery, CurrentDemand, WeldingDetection
  and SessionStop.

The codec's own limits are kept as generated. A response with more than this fails to decode:
* ServiceList: 8 services. Value-added services offered by the charger are decoded and can be ignored.
* PaymentOptionList: 2 options.
* SAScheduleList: 3 tuples, each with up to 5 PMaxSchedule entries and an optional SalesTariff of up to 5 entries.
* Signed messages (a header signature, for example a signed SalesTariff) don't decode.

## One document for encoder and decoder

With `SHARED_EXI_DOC=1`, the decoded response and the next request are in the same memory. Every place on main's DIN
path that reads a response after the next request has been prepared or encoded:

| State | What happens | With one document |
|---|---|---|
| WaitForContractAuthenticationResponse, not finished | `encodeAndTransmit()` sends the request again from the encoder document, without preparing it again | **Breaks**: the document now holds the decoded response. Needs the request built again (as ChargeParameterDiscovery and CableCheck do). |
| WaitForCurrentDemandResponse | reads `DC_EVSEStatus.EVSEStatusCode` three times, and `EVSEPresentVoltage`/`EVSEPresentCurrent` at the end; the Malfunction, EmergencyShutdown and inlet-voltage branches call `pev_sendPowerDeliveryReq(0)` in between | **Breaks**: after a PowerDeliveryReq is prepared, the later checks read the request instead of the response. Needs a copy of the status code, voltage and current right after decoding. |
| SessionSetup | session ID copied before the next request | Safe |
| ServiceDiscovery, ServicePaymentSelection, PowerDelivery, SessionStop | only `..._isUsed` read, before the next request | Safe |
| ChargeParameterDiscovery | limits read before the next request; the retry builds its request again | Safe |
| CableCheck | `ResponseCode`, `EVSEProcessing` copied to locals first; the retry builds its request again | Safe |
| PreCharge | present voltage read before any request; requests are built again | Safe |
| WeldingDetection | present voltage read first; requests are built again | Safe |
| SupportedAppProtocol | `aphsDoc` is a separate document | Safe |

TCP retransmissions use the TCP transmit buffer, not the document.

Found on the way, independent of the shared document: in WaitForCurrentDemandResponse, the EVSE_Malfunction,
EVSE_EmergencyShutdown and inlet-voltage branches send PowerDeliveryReq(0) but don't leave the function. Unless the
battery is full or a stop was requested, the last `else` then also sends a CurrentDemandReq and returns to
WaitForCurrentDemandResponse.

## What else blocks ISO on main

Checked against main (54bcecd); to be fixed in phase 1, not here:
* **TCP receive.** `tcp_rxdata` is 200 bytes (`TCP_RX_DATA_LEN`). A segment with 200 bytes of payload or more is
  ignored without an ACK. There is no reassembly: one segment is taken as one V2GTP message. Yet the SYN advertises
  an MSS of 1440 and every segment a window of 1000 bytes.
* **Ethernet receive.** `MY_ETH_RECEIVE_BUFFER_LEN` is 250, so a frame is cut to 250 bytes: at most 176 bytes of TCP
  payload. `evaluateTcpPacket` still copies the length from the TCP/IP headers. For 177 to 199 bytes it reads past
  the copied frame, beyond the end of `myethreceivebuffer`.
* **TCP options.** The payload is copied from a fixed offset (`myethreceivebuffer[74]`), which assumes a 20-byte TCP
  header. A charger that sends options (for example timestamps) in its data segments would be misread; the header
  length is computed but not used for the copy.
* **SDP.** Clara asks for security 0x10 (no TLS) and transport 0x00 (TCP), but the response's security and transport
  bytes are not checked. A charger that answers with TLS would get plain TCP.
* **RAM for a 1 kB receive path** (V2G messages up to 1,024 bytes):
  * `myethreceivebuffer` 250 → 1,100: +850 (Ethernet 14 + IPv6 40 + TCP 20 + 1,024);
  * `tcp_rxdata` 200 → 1,032: +832 (V2GTP 8 + 1,024, and room for reassembly);
  * `mySpiRxBuffer`, already 1,100: about +12 for the SPI framing of a full frame;
  * a smaller MSS and window in `tcp.cpp`: no RAM.

  About 1.7 kB in all, against 29 kB left for the stack today (43 kB with one shared document).
